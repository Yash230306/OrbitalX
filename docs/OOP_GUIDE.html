1. Main Objective & Pedagogical Foundation

1.1 The Primary Objective: An OOP Software Project

The primary goal of OrbitalX is to serve as an authoritative, real-world demonstration of Object-Oriented Programming (OOP) and clean software design.

When learning programming, students are frequently taught OOP through simplistic, disconnected textbook examples like Dog extends Animal or Car extends Vehicle. While helpful for introducing syntax, these examples fail to teach how OOP solves real engineering dilemmas:

  • How do dozens of collaborating objects communicate without turning into an unmaintainable "spaghetti" codebase?
  • How do we ensure that an object's internal data cannot be placed into an illegal or corrupted state by other threads or user interfaces?
  • How can new features (such as a new type of rocket engine, or a new cosmic hazard) be introduced without altering existing, tested code?
  • How can graphical interfaces (GUI) and console terminals (CLI) operate simultaneously against the same core simulation without duplicating business logic?

OrbitalX answers these questions directly. It treats the space mission simulator as a concrete, engaging case study. Every spacecraft, fuel tank, sensor, and mission rule is an object with strict responsibilities, clear public contracts, and private data invariants.

1.2 Why Space Simulation Is the Ideal Domain for OOP

An aerospace mission control system is uniquely suited for studying Object-Oriented design because physical spacecraft are inherently modular:

Real-World Spacecraft Reality Software Engineering Challenge OOP Solution in OrbitalX
Physical Subsystems: Spacecraft comprise engines, fuel cells, life support scrubbers, and guidance gyros. State must be modularized; a failure in thermal cooling must not corrupt fuel calculations. Encapsulation & Composition: Spacecraft composes independent Subsystem objects that manage their own state.
Diverse Component Variants: Different missions use chemical thrusters, ion engines, or nuclear thermal engines. The flight loop must execute propulsion without hardcoding every possible engine type. Polymorphism: Base Subsystem defines applyPhysics(); subclasses implement unique thrust formulas.
Telemetry Stream Validation: Sensors produce noisy, volatile analog readings. Raw values must be cached, filtered, and checked against safety thresholds. Decorator Pattern & Interfaces: Sensor interface is wrapped by NoiseDecorator and DriftDecorator.
Emergency Responses: Remediations require automatic action, crew intervention, or ground commands. Actions must be queued, previewed, executed, and rolled back safely. Command Pattern & Chain of Responsibility: Remediations are first-class CorrectiveAction objects.

1.3 Rule-Based Simulation vs. Complex Physics

Design Principle: Simplicity in Physics, Excellence in Architecture: OrbitalX intentionally avoids complicated numerical calculus, N-body gravitational integration, or orbital aerodynamics. Instead, it employs an intuitive, rule-based discrete simulation (updating once every 1-second "tick"). This guarantees that the code remains clean, deterministic, beginner-friendly, and 100% focused on Object-Oriented architecture rather than advanced astrophysics.

2. Project Overview: The Seven Pillars of OrbitalX

To understand the classes and their interactions, we must first understand the user-facing capabilities of OrbitalX. The simulator allows users to perform seven core workflows:

1. Spacecraft Configuration

Users select craft specifications (e.g., Explorer, Cargo Hauler, Fast Probe). Each specification configures base fuel capacity, dry mass, structural integrity, and initial consumable inventories.

2. Component Integration

The spacecraft is assembled from discrete hardware components: main and backup rocket engines, multi-chamber fuel tanks with isolated reserve supplies, battery arrays, photovoltaic solar wings, and COâ‚‚ scrubbers.

3. Mission Planning

A flight profile is created targeting destinations like Low Earth Orbit (LEO), the Moon, Mars, or Europa. Each destination establishes distance, environmental radiation baselines, and radio transmission latency (uplink delay).

4. Real-Time Flight Simulation

The simulation engine executes a synchronized clock tick (default 1 to 20 ticks/sec). Each tick advances spacecraft distance, burns propellant based on throttle settings, updates battery power, and simulates thermal dissipation.

5. Telemetry & Sensor Monitoring

Flight directors monitor critical instruments in real time: fuel remaining, throttle percentage, velocity, cabin pressure, oxygen concentration, battery state-of-charge, engine temperature, and cosmic radiation.

6. Failure Simulation & Recovery

Fifteen dynamic hardware faults can occur (fuel leaks, solar array degradation, thruster clogs, gyro drift, computer crashes, hull breaches). Systems recover via automated self-healing, autopilot rules, crew spacewalks (EVA), or manual ground commands.

7. Mission Analytics, Replay & Reporting

Upon mission conclusion (or during flight), the complete telemetry history can be scrubbed backward and forward using a time-travel slider. Automated reporting visitors compile mission dossiers into formatted HTML dashboards or CSV telemetry sheets, computing an objective performance grade (S, A, B, C, or F).

3. Step-by-Step Object-Oriented Programming Concepts

Concept A: Classes and Objects

1 What is the concept?
A Class is a user-defined blueprint or template that defines the structure (attributes/state) and behavior (methods) common to all entities of a certain type. An Object is a concrete, self-contained instance of that class created in memory with its own distinct state.

2 Why do we need it?
Without classes and objects, code must rely on disconnected primitive variables (e.g., craft1_fuel, craft1_speed, craft2_fuel, craft2_speed). This approach quickly becomes unmanageable, bug-prone, and impossible to scale when multiple spacecraft are active.

3 Explain it in very simple language:
Think of a class as an architectural blueprint for a spacecraft. The blueprint specifies that every spacecraft must have a fuel level, an engine, and a throttle. An object is an actual physical spacecraft built using that blueprint (e.g., Spacecraft #1 named "Apollo" and Spacecraft #2 named "Orion"). Both follow the same blueprint, but Apollo might have 80% fuel while Orion has 30% fuel.

4 How is it implemented in OrbitalX?
The blueprint is com.orbitalix.model.Spacecraft. During simulation setup or what-if scenario testing, multiple Spacecraft objects are instantiated in memory, each configured with specific mass, engine performance, and consumable levels.

5 Which classes and files are involved?
src/main/java/com/orbitalix/model/Spacecraft.java (Blueprint), com/orbitalix/config/MissionConfig.java (Configuration object), and com/orbitalix/simulation/SimulationEngine.java (Instantiator).

Concept B: Encapsulation

1 What is the concept?
Encapsulation is the practice of bundling data (fields) and the methods that operate on that data into a single unit (class), while restricting direct access to the internal state from the outside world using access modifiers (private).

2 Why do we need it?
If class variables are public, any external class (such as a GUI slider, an autopilot script, or a network thread) can directly overwrite them (e.g., craft.fuel = -500; or craft.throttle = 9999;). This causes silent logic errors, inconsistent state, and catastrophic simulation crashes.

3 Explain it in very simple language:
Think of an ATM machine or a car's fuel tank. You cannot open the fuel tank with a blowtorch and manually adjust the gasoline level inside. Instead, you interact with controlled access points: the fuel nozzle (to add fuel) and the engine fuel line (to consume fuel). The tank itself verifies how much fuel it holds and prevents overflowing or negative values.

4 How is it implemented in OrbitalX?
In FuelTank.java and Spacecraft.java, all physical telemetry variables (level, reserveLevel, throttle, pressure) are declared private. Outside classes can only query values through public getters (e.g., level()) and modify values through validated domain methods (e.g., consume(amount), crossFeed(amount)).

5 Which classes and files are involved?
src/main/java/com/orbitalix/resource/Resource.java, src/main/java/com/orbitalix/resource/FuelTank.java, and src/main/java/com/orbitalix/model/Spacecraft.java.

6 Small code example from the project:

// From FuelTank.java and Resource.java
public abstract class Resource {
    private final double capacity;
    private double level; // Strictly private: cannot be touched directly from outside

    // Controlled Getter: Exposes current state read-only
    public final synchronized double level() { return level; }

    // Controlled Mutator: Enforces business logic invariants
    public final synchronized double consume(double amount) {
        if (!Double.isFinite(amount) || amount < 0) {
            throw new IllegalArgumentException("Consumption amount must be non-negative");
        }
        double actual = Math.min(amount, level);
        level -= actual; // Guarantees level can NEVER drop below 0
        return actual;
    }
}

7 Code explanation line by line:

Lines 2â€“4Declares capacity as final (immutable once constructed) and level as private. No external class can write fuelTank.level = 0.
Lines 6â€“7Public getter level() provides read-only visibility into current reserves. Marked synchronized to ensure thread safety across UI and simulation threads.
Lines 9â€“17The consume() method validates that the requested amount is a finite, positive number. It clamps the deduction using Math.min(amount, level) so fuel can never become negative.

8 How the classes interact:
The PropulsionSubsystem asks the Spacecraft to consume fuel for a thruster burn. The spacecraft calls fuel.consume(burnAmount) on its internal FuelTank object. The fuel tank verifies its own reserves, deducts the amount safely, and returns the exact amount burned back to propulsion.

9 Practical engineering benefit:
Total protection against corrupted state. If an anomaly injector or runaway loop requests 10,000 liters of fuel when only 50 liters remain, the system cleanly consumes 50 liters, sets remaining fuel to exactly 0, and signals an engine flameout instead of generating nonsensical negative fuel.

Concept C: Abstraction

1 What is the concept?
Abstraction is the principle of hiding internal implementation complexity and exposing only a clean, simple, essential interface to users and collaborating objects.

2 Why do we need it?
Without abstraction, every part of the application would need to know the intricate internal formulas of every other component. The dashboard GUI would need to know Ohm's law to display battery status, and the mission clock would need to calculate thermodynamic radiation equations to advance time.

3 Explain it in very simple language:
Think of the gas pedal and steering wheel in a car. To accelerate, you press the gas pedal. You do not need to know how fuel injection nozzles squirt gasoline into the cylinder, how the spark plug fires, or how the crankshaft rotates. The pedal is an abstraction that hides that complexity.

4 How is it implemented in OrbitalX?
OrbitalX defines clean abstractions using abstract classes like Subsystem.java and interfaces like SimulationController.java. The SimulationEngine does not know the internal physics of individual hardware parts; it simply invokes subsystem.tick(craft, env) on an abstract subsystem reference.

5 Which classes and files are involved?
src/main/java/com/orbitalix/model/Subsystem.java (Abstract Class), src/main/java/com/orbitalix/api/SimulationController.java (Interface), and src/main/java/com/orbitalix/simulation/SimulationEngine.java.

6 Small code example from the project:

// High-level Abstraction: Subsystem.java
public abstract class Subsystem {
    private final String name;
    
    public Subsystem(String name) { this.name = name; }

    // Public Abstract Method: The contract exposed to the simulation
    protected abstract void applyPhysics(Spacecraft craft, SpaceEnvironment environment);

    // Template Method: Coordinates execution uniformly
    public final void tick(Spacecraft craft, SpaceEnvironment environment) {
        applyPhysics(craft, environment); // Dispatches to the concrete implementation
        updateSensorCache();
    }
}

7 Code explanation line by line:

Lines 1â€“4Declares Subsystem as an abstract class. It cannot be directly instantiated with new Subsystem() because an abstract subsystem does not have specific physical behavior.
Lines 6â€“8The abstract method applyPhysics(...). It declares a behavioral contract with no body, mandating that any subclass (such as propulsion or thermal) must provide its own specific physics formulas.
Lines 10â€“14The public concrete method tick(...). This is the simple operation exposed to the outside world. Any caller simply calls subsystem.tick(craft, env) without needing to understand the underlying physics.

8 How the classes interact:
The Spacecraft maintains a List<Subsystem>. On every simulation second, it iterates over the list and invokes subsystem.tick(this, env). It interacts purely through the Subsystem abstraction without caring whether a given element is a thermal radiator, a chemical rocket, or an avionics computer.

9 Practical engineering benefit:
Massive simplification. Developers can write brand-new subsystem models (e.g., an experimental Ion Propulsion Engine or a Nuclear Reactor) by extending Subsystem and implementing applyPhysics(), without changing a single line of code in Spacecraft.java, SimulationEngine.java, or the UI.

Concept D: Inheritance

1 What is the concept?
Inheritance is a mechanism where a new class (subclass or child) derives attributes and behaviors from an existing class (superclass or parent), modeling an "IS-A" relationship and promoting code reusability.

2 Why do we need it?
Spacecraft components share dozens of common attributes and behaviors: each has an identifier, a list of diagnostic sensors, health status, and active fault tracking. Without inheritance, every single component class would have to duplicate 100+ lines of identical sensor and fault management code.

3 Explain it in very simple language:
Think of a family tree. A parent has common traits (eyes, DNA, blood type). The children inherit all these traits automatically without having to recreate them, but each child can also have their own unique skills (one child is a musician, another is a pilot).

4 How is it implemented in OrbitalX?
OrbitalX creates rich inheritance hierarchies for hardware subsystems, consumables, and crew members:

  • Subsystem (Parent) → PropulsionSubsystem, ThermalSubsystem, LifeSupportSubsystem, PowerSubsystem, AttitudeSubsystem
  • Resource (Parent) → FuelTank, Battery, OxygenSupply, SealantStock
  • CrewMember (Parent) → Commander, FlightEngineer, MedicalOfficer, Pilot

5 Which classes and files are involved?
src/main/java/com/orbitalix/model/Subsystem.java and src/main/java/com/orbitalix/model/PropulsionSubsystem.java.

6 Small code example from the project:

// Child Class: PropulsionSubsystem.java inheriting from Subsystem
public final class PropulsionSubsystem extends Subsystem {
    
    public PropulsionSubsystem(Spacecraft owner) {
        // Reuses parent constructor to initialize sensors and name
        super("Propulsion", List.of(new TemperatureSensor("engine-temp", owner::temperature)));
    }

    // Specializes parent behavior with unique rocket propulsion physics
    @Override
    protected void applyPhysics(Spacecraft craft, SpaceEnvironment env) {
        if (hasFault(FaultType.ENGINE_MISFIRE)) {
            craft.degradeEngineEfficiency(0.45);
        }
        double burnRate = craft.throttle() * 0.05;
        craft.consumeFuel(burnRate);
    }
}

7 Code explanation line by line:

Line 2The keyword extends Subsystem establishes that PropulsionSubsystem IS-A Subsystem. It inherits all fields and methods from Subsystem.
Lines 4â€“7The super(...) statement delegates to the parent constructor, reusing the parent's sensor list registration and health tracking code.
Lines 9â€“17The @Override annotation indicates that applyPhysics specializes the abstract method defined in the parent class, implementing specific rocket fuel burn equations.

8 How the classes interact:
When subsystem.health() is called on a PropulsionSubsystem, the call executes logic written once in the parent class Subsystem.java. When subsystem.tick() is called, execution flows from parent template down to child applyPhysics().

9 Practical engineering benefit:
Over 60% reduction in boilerplate code across the five subsystem implementations. When a bug was fixed in fault status tracking, updating the single parent class Subsystem.java instantly updated all five subsystem types across the spacecraft.

Concept E: Polymorphism

1 What is the concept?
Polymorphism (Greek for "many forms") is the ability of different classes to respond to the same method invocation in their own unique way. In Java, this occurs via Method Overriding (Runtime Polymorphism) and Method Overloading (Compile-time Polymorphism).

2 Why do we need it?
Without polymorphism, a coordinator class must check the concrete type of every object using nested if-else or switch-case statements (e.g., if (s instanceof Propulsion) ... else if (s instanceof Thermal) ...). This creates brittle code that breaks every time a new component is added.

3 Explain it in very simple language:
Think of the command "Speak!" given to different animals. If you say "Speak" to a dog, it says "Woof". If you say "Speak" to a cat, it says "Meow". You issue the exact same command, but each animal responds according to its own nature.

4 How is it implemented in OrbitalX?
The Spacecraft holds a polymorphic collection: List<Subsystem>. During every tick, it loops through the collection and executes s.applyPhysics(craft, env). At runtime, Java automatically invokes the PropulsionSubsystem implementation for engines, the ThermalSubsystem implementation for radiators, and the LifeSupportSubsystem implementation for oxygen scrubbers.

5 Which classes and files are involved?
src/main/java/com/orbitalix/model/Spacecraft.java, com/orbitalix/model/Subsystem.java, PropulsionSubsystem.java, ThermalSubsystem.java, and LifeSupportSubsystem.java.

6 Small code example from the project:

// In Spacecraft.java: Polymorphic Dispatch Loop
public synchronized void tick(SpaceEnvironment environment) {
    // Heterogeneous list of subsystems treated polymorphically
    for (Subsystem subsystem : this.subsystems) {
        // Dynamic Method Dispatch: calls the specific child implementation!
        subsystem.tick(this, environment);
    }
}

// Overloading Example in FuelTank.java (Compile-Time Polymorphism)
public FuelTank(double capacity, double initialLevel) {
    this(capacity, initialLevel, 20.0, 20.0); // Overloaded: uses default reserve
}
public FuelTank(double capacity, double initialLevel, double resCap, double resLevel) {
    super("Fuel", "%", capacity, initialLevel); // Full constructor
}

7 Code explanation line by line:

Lines 2â€“7The loop iterates through this.subsystems using the base type reference Subsystem. At runtime, the JVM inspects the actual object type in memory and dispatches the call to the appropriate child class method (Dynamic Method Dispatch).
Lines 10â€“15Demonstrates Method Overloading. Two constructors exist with the same name (FuelTank) but different parameter signatures, allowing callers flexibility during object initialization.

8 How the classes interact:
The Spacecraft interacts with its child components strictly through the supertype Subsystem. The child classes (ThermalSubsystem, PowerSubsystem) polymorphically mutate different aspects of the spacecraft (battery levels, temperature, cabin oxygen) without the spacecraft needing a single instanceof check.

9 Practical engineering benefit:
Full adherence to the Open/Closed Principle. If NASA commissions a new Scientific Sensor Payload Subsystem, we write a single class extending Subsystem and add it to the list. The central tick engine works with the new subsystem immediately without modifying the simulation loop.

Concept F: Association, Aggregation, and Composition

1 What is the concept?
Object-Oriented systems are not single classes; they are networks of collaborating objects. Object relationships describe how classes connect, share data, and manage each other's lifecycles:

  • Association: A loose "uses-a" relationship where independent objects communicate.
  • Aggregation: A "has-a" relationship where the whole contains parts, but parts can exist independently.
  • Composition: A strong "part-of" relationship where the parent owns the lifecycle of the child parts.

2 Why do we need it?
Different physical relationships have different memory management and lifecycle rules. If a spacecraft is destroyed, its engine is destroyed (Composition). But an astronaut on that spacecraft can be transferred to another mission (Aggregation). Modeling these distinctions correctly prevents memory leaks and orphaned states.

3 Explain it in very simple language:

  • Association: A pilot flies an airplane. When the flight ends, both the pilot and airplane continue to exist independently.
  • Aggregation: A bag contains books. If you throw the bag away, the books still exist; you can put them in another bag.
  • Composition: A human body has a heart. If the body ceases to exist, the heart ceases to exist as an operating component.

4 How is it implemented in OrbitalX?
OrbitalX strictly models all three:

  • Association: Mission and Spacecraft. A Mission is planned with a target Spacecraft. They are peers; a Spacecraft can outlive an individual mission.
  • Aggregation: Spacecraft and CrewMember. Astronauts are assigned to a spacecraft roster, but exist independently and can be reassigned between missions.
  • Composition: Spacecraft and FuelTank / Subsystem. The internal tanks and subsystems are instantiated inside the spacecraft constructor and cannot exist apart from their owning craft.

Concept G: Interfaces and Abstract Classes

1 What is the concept?
An Interface is a pure behavioral contract specifying what an implementing class must do, with no instance state (variables). An Abstract Class is a partial implementation that provides common state and concrete methods while leaving specific methods to be completed by subclasses.

2 Why do we need it?
Java supports single inheritance for classes (a class can only extend one superclass), but supports multiple inheritance for interfaces (a class can implement multiple interfaces). Knowing when to use an abstract class versus an interface is the hallmark of professional software design.

3 Explain it in very simple language:
An Interface is like a USB specification. It doesn't care if you plug in a mouse, a keyboard, or a rocket sensor; as long as the device has the physical USB shape and speaks the protocol, it works. An Abstract Class is like a half-built kit car: it already has wheels, an chassis, and a steering column, but you must choose what engine to install before driving it.

4 How is it implemented in OrbitalX?
OrbitalX pairs pure interfaces with abstract base classes across the entire codebase:

Domain Area Interface (Pure Contract) Abstract Class (Partial Implementation)
Sensor Telemetry sensor.Sensor (defines read(), unit()) sensor.BaseSensor (caches readings, ring buffers)
Corrective Actions action.CorrectiveAction (defines execute()) action.AbstractCorrectiveAction (manages IDs, risk ratings)
Physical Subsystems model.SystemComponent (defines id(), health()) model.Subsystem (binds sensor lists, handles faults)
Event Notification api.TickListener, api.MissionEventListener Pure listeners: implemented directly by GUI views

// 1. The Pure Interface: Sensor.java
public interface Sensor {
    Reading read(); // Abstract contract: must return a telemetry reading
    String unit();
    default double latest() { return read().value(); } // Default utility method
}

// 2. The Abstract Base Class: BaseSensor.java
public abstract class BaseSensor implements Sensor {
    private final String id;
    private final RingBuffer<Reading> history = new RingBuffer<>(60);

    protected BaseSensor(String id) { this.id = id; }

    // Concrete implementation of interface methods with shared caching logic
    @Override
    public final Reading read() {
        double raw = sampleRaw(); // Calls the abstract template method below
        Reading reading = new Reading(raw, unit());
        history.add(reading);
        return reading;
    }

    // Primitive abstract hook: concrete subclasses implement physical sampling
    protected abstract double sampleRaw();
}

7 Code explanation line by line:

Lines 2â€“6Sensor is an interface declaring the methods read() and unit(). It contains no state variables.
Lines 9â€“14BaseSensor implements Sensor. It introduces state (id and a 60-sample RingBuffer) that all sensors share.
Lines 16â€“22Implements the Template Method pattern: read() handles history tracking and delegates to sampleRaw().
Line 25sampleRaw() is declared abstract, compelling subclasses (like TemperatureSensor) to provide the actual telemetry measurement logic.

The anomaly detector (ThresholdDetector) interacts solely with the Sensor interface. Concrete sensors (like TemperatureSensor) inherit history buffering from BaseSensor, while decorators (like NoiseDecorator) wrap the Sensor interface dynamically.

9 Practical engineering benefit:
Decouples measurement consumers from measurement providers. We can introduce synthetic mock sensors in unit tests or decorate live sensors with simulated radiation interference without changing the detection engine.

Concept H: SOLID Principles in OrbitalX

SOLID is an acronym for five foundational software engineering design principles formulated by Robert C. Martin ("Uncle Bob"). In OrbitalX, these principles transform a complex, real-time aerospace simulator into an elegant, maintainable, and easily extensible architecture:

S 1. Single Responsibility Principle (SRP)

Definition: "A class should have one, and only one, reason to change." Each class must focus purely on a single cohesive responsibility.

In Simple Language: If a class does physics calculations, saves files to disk, and draws UI buttons, any change to UI buttons risks breaking the physics calculations. Give each job to a separate specialist class.

Implementation in OrbitalX: DetectionEngine.java does only anomaly detection across telemetry streams. It does not decide how to resolve anomalies (that is AdvisorEngine's job), does not execute fixes (that is AutopilotController's job), and does not draw graphics (that is DashboardView's job). 

// DetectionEngine.java has ONE single reason to change: anomaly detection algorithms
public final class DetectionEngine {
    private final List<AnomalyDetector> detectors = new ArrayList<>();

    public synchronized List<Anomaly> scan(Spacecraft craft) {
        List<Anomaly> detected = new ArrayList<>();
        for (AnomalyDetector detector : detectors) {
            detector.evaluate(craft).ifPresent(detected::add);
        }
        return Collections.unmodifiableList(detected);
    }
}

Architectural Benefit: When tuning statistical anomaly thresholds or adding ML-based anomaly models, only DetectionEngine is modified. GUI views, database reporters, and flight mechanics remain untouched.

O 2. Open/Closed Principle (OCP)

Definition: "Software entities should be open for extension, but closed for modification." You should be able to introduce new behavior without editing existing, working source code.

In Simple Language: Think of a smartphone with an app store. When you want a new calculator feature, you don't solder new circuits onto the motherboard; you download an app that plugs into the existing phone operating system.

Implementation in OrbitalX: All emergency responses implement the CorrectiveAction interface. When we added SealHullBreachAction, RebootAvionicsAction, and EvasiveManeuverAction, we did not modify a single line of SimulationEngine.java. The engine simply executes any CorrectiveAction polymorphically. 

// Open for extension: New actions simply extend AbstractCorrectiveAction without modifying the engine
public final class SealBreachAction extends AbstractCorrectiveAction {
    public SealBreachAction() {
        super("ACT-SEAL", "Deploy Emergency Nanogel Sealant", RiskLevel.LOW);
    }

    @Override
    public ExecutionResult execute(Spacecraft craft) {
        craft.sealBreaches();
        return ExecutionResult.success("Hull integrity restored to 100%");
    }
}

Architectural Benefit: Zero risk of regression. New aerospace failure recoveries can be introduced as standalone classes without touching the battle-tested simulation core.

L 3. Liskov Substitution Principle (LSP)

Definition: "Subtypes must be substitutable for their base types without altering program correctness." Subclasses must honor the full behavioral contract of their parent classes.

In Simple Language: If it looks like a duck and quacks like a duck, but needs batteries, it is not a real duck! A subclass should never throw unexpected exceptions or violate parent assumptions.

Implementation in OrbitalX: Any class implementing Sensor (such as TemperatureSensor, PressureSensor, or the wrapped NoiseDecorator) can be passed to ThresholdDetector. The detector reads telemetry values seamlessly without needing special if (sensor instanceof NoiseDecorator) checks. 

// Liskov Substitution in action: Decorators seamlessly substitute for Base Sensors
Sensor physicalSensor = new TemperatureSensor("CABIN-TEMP");
Sensor noisySensor = new NoiseDecorator(physicalSensor, 0.05); // Liskov substitutable!

// Client code works uniformly with either instance
ThresholdDetector detector = new ThresholdDetector(noisySensor, 15.0, 30.0);
Reading current = detector.sample(); // Works identically without breaking invariant contracts

Architectural Benefit: Enables plug-and-play sensors, test doubles, and synthetic fault injectors without causing unexpected runtime crashes.

I 4. Interface Segregation Principle (ISP)

Definition: "Clients should not be forced to depend upon interfaces that they do not use." Many small, specific interfaces are better than one general-purpose interface.

In Simple Language: Don't give a customer a 500-page encyclopedia when they only asked for the local weather forecast.

Implementation in OrbitalX: Instead of one giant ISpacecraftController with 60 methods, OrbitalX defines small, segregated, single-purpose interfaces: TickListener (1 method: onTick()), MissionEventListener (1 method: onEvent()), Copyable<T> (1 method: copy()), and Identifiable (1 method: id()). 

// Small, Segregated Interfaces:
public interface TickListener {
    void onTick(SimulationSnapshot snapshot); // Only depends on clock updates
}

public interface MissionEventListener {
    void onMissionEvent(MissionEvent event); // Only depends on milestone events
}

// GUI components implement only what they need:
public class TelemetryGraphPanel implements TickListener {
    @Override public void onTick(SimulationSnapshot s) { updateGraph(s); }
    // Does NOT need to implement dummy stubs for onMissionEvent, audio alarms, or database exports!
}

Architectural Benefit: Eliminates "fat" interfaces and empty boilerplate stubs. UI widgets only listen to ticks, audio systems only listen to critical alarms, and loggers only listen to events.

D 5. Dependency Inversion Principle (DIP)

Definition: "High-level modules should not depend on low-level modules. Both should depend on abstractions."

In Simple Language: In your home, electrical appliances (lamps, laptops) do not solder directly into the city power grid cables. Both appliances and the power grid connect through standard wall electrical sockets (the abstraction).

Implementation in OrbitalX: High-level GUI panels (like DashboardView, CutawayView, and CrewView) do not depend on the low-level, concrete SimulationEngine.java. Instead, both the GUI and the engine depend on the public abstract interface SimulationController in com.orbitalix.api. 

// High-level GUI depends on abstract interface, NOT concrete simulation engine
public class DashboardView extends BaseView {
    private final SimulationController controller; // Depends on Abstraction!

    public DashboardView(SimulationController controller) {
        this.controller = Objects.requireNonNull(controller);
    }

    public void onThrottleSliderMoved(int newThrottle) {
        controller.setThrottle(newThrottle); // Decoupled dispatch!
    }
}

Architectural Benefit: Complete decoupling of Presentation from Physics. In headless automated test suites or what-if forecast sandboxes, a lightweight mock controller is substituted without modifying a single line of GUI code.

4. Complete Project Architecture: Clean 3-Tier Layering

4.1 The 3-Tier Architectural Hierarchy

OrbitalX is structured according to a classic Layered Architecture. Each layer has strict, isolated responsibilities and communicates across well-defined boundaries:

+--------------------------------------------------------------------------+ | 1. PRESENTATION LAYER | | [DashboardView] [CutawayView] [CrewView] [OrbitView] [ConsoleCLI] | | - Java2D View Rendering - User Click / Keyboard Capture | | - 60 FPS HUD Animations - Audio Synthesizer Triggers | +--------------------------------------------------------------------------+ | (Calls Methods on api.SimulationController Facade) (Receives Immutable SimulationSnapshot Records) v +--------------------------------------------------------------------------+ | 2. DOMAIN / BUSINESS LOGIC LAYER | | [SimulationEngine] [Spacecraft] [Subsystems] [Crew] [OperatingLimits] | | [DetectionEngine] [AdvisorEngine] [AutopilotController] [Actions] | | - Deterministic Tick Loop - Propulsion / Thermal Physics | | - Anomaly Detection - Autonomous Response Chains | +--------------------------------------------------------------------------+ | (Dumps Historical State Records & Audit Events) (Saves / Restores Configuration and Scenarios) v +--------------------------------------------------------------------------+ | 3. PERSISTENCE & DATA LAYER | | [History<T>] [MissionReport] [MissionRecorder] [ScenarioFactory] | | - Time-Travel Telemetry Ring Buffer (Memento Pattern) | | - HTML5 & CSV Telemetry File Exporters (Visitor Pattern) | | - Scenario Seed Data & Destination Profiles | +--------------------------------------------------------------------------+

4.2 Why Layers Are Strictly Separated

  • Zero Physics in the GUI: A common amateur mistake is embedding calculation formulas inside button click listeners (e.g., subtracting fuel directly inside a button handler). In OrbitalX, GUI classes contain zero physics. If the entire Swing GUI is replaced with a JavaFX or Web interface, not a single line of simulation logic changes.
  • Headless Testability: Because business logic is strictly decoupled from presentation, the automated test suite (Main --selftest) executes all 108 mission scenarios, detects anomalies, and validates autopilot recovery at 10,000 ticks/sec headlessly in CI without instantiating a single window or canvas.
  • Thread Safety via Immutable Records: The simulation engine runs on a background timer thread, while the GUI renders on the Swing Event Dispatch Thread (EDT). To prevent race conditions, the engine never exposes mutable internal objects to the UI. Instead, it projects state into immutable Java 17 record snapshots (e.g., SimulationSnapshot, CrewSnapshot). The UI can read these records concurrently without synchronization locks.

5.2 Deep Dive into the Ten Key Classes

1. Spacecraft.java (com.orbitalix.model)

  • Purpose: The central domain model representing the physical aerospace vessel.
  • Responsibilities: Owns the component topology, maintains operational limits, tracks physical metrics (fuel, oxygen, pressure, temperature), and updates child subsystems.
  • Collaborators: Composes FuelTank, Battery, OxygenSupply, CrewRoster; aggregates Subsystem list; updates SpacecraftState.
  • OOP Concepts: Encapsulation, Composition, State Pattern, SystemComponent interface.
  • Why separate: Isolates spacecraft physical state from mission trajectory and rendering logic.

2. Engine / PropulsionSubsystem.java (com.orbitalix.model)

  • Purpose: Models main rocket propulsion, throttle response, and engine misfire failures.
  • Responsibilities: Calculates instantaneous thrust output, coordinates fuel consumption with the tank, and simulates thermal output based on throttle percentage.
  • Collaborators: Extends Subsystem; mutates Spacecraft; monitors TemperatureSensor.
  • OOP Concepts: Inheritance, Polymorphism (method overriding), Abstraction.
  • Why separate: Keeps propulsion equations isolated from electrical and life support logic.

3. FuelTank.java (com.orbitalix.resource)

  • Purpose: Encapsulates spacecraft propellant storage and cross-feed valves.
  • Responsibilities: Tracks main tank level, protects isolated reserve tanks, performs cross-feed transfers, and estimates ticks until fuel exhaustion.
  • Collaborators: Extends Resource; used directly by PropulsionSubsystem.
  • OOP Concepts: Encapsulation, Defensive validation, Overloading, Thread synchronization.
  • Why separate: Reusable across chemical rockets, RCS pods, and lander descent stages.

4. Mission.java (com.orbitalix.model)

  • Purpose: Represents a planned flight profile toward a specific celestial destination.
  • Responsibilities: Advances distance traveled, calculates orbital trajectory, checks mission completion criteria (Destination Reached, Fuel Exhausted, Oxygen Lost).
  • Collaborators: Associates with Spacecraft and Destination; owns OrbitModel.
  • OOP Concepts: Association, High Cohesion, Domain Modeling.
  • Why separate: Allows the same Spacecraft object to fly different mission profiles sequentially.

5. SimulationEngine.java (com.orbitalix.simulation)

  • Purpose: The central conductor and coordinator of the entire simulation universe.
  • Responsibilities: Advances the master clock tick, executes fault schedules, coordinates detection/advisor engines, manages command channels, and records history snapshots.
  • Collaborators: Composes DetectionEngine, AdvisorEngine, EventBus, History, Spacecraft, Mission.
  • OOP Concepts: Facade Pattern, Orchestration, Single Responsibility (Coordination).
  • Why separate: Centralizes the simulation loop, preventing distributed timing chaos.

6. FailureManager & Autopilot (com.orbitalix.autonomy & advisor)

  • Purpose: Manages fault diagnostics and multi-tiered autonomous recovery.
  • Responsibilities: AdvisorEngine matches anomalies to rules. AutopilotController evaluates risk through a Chain of Responsibility (SelfHealingHandler → AutopilotHandler → CrewHandler → EscalationHandler) and executes corrective commands.
  • Collaborators: Reads Anomaly; executes CorrectiveAction commands against Spacecraft.
  • OOP Concepts: Chain of Responsibility, Strategy Pattern, Command Pattern.
  • Why separate: Isolates decision-making logic from physical spacecraft mechanics.

7. MissionService / DefaultSimulationController.java (com.orbitalix.simulation)

  • Purpose: The public service facade exposing safe operations to GUI and CLI clients.
  • Responsibilities: Implements SimulationController interface. Mediates commands (throttle, pause, resume, assign crew, execute advice) and publishes immutable state snapshots.
  • Collaborators: Delegates to SimulationEngine; consumed by MainWindow, DashboardView, and CLI.
  • OOP Concepts: Facade Pattern, Dependency Inversion Principle, Information Hiding.
  • Why separate: Prevents presentation code from directly manipulating internal engine pointers.

8. SpacecraftRepository / History.java (com.orbitalix.replay)

  • Purpose: In-memory historical state repository allowing time-travel telemetry scrubbing.
  • Responsibilities: Stores an immutable ring-buffer of up to 600 past simulation ticks; retrieves past snapshots for replay, comparison, and post-mission analytics.
  • Collaborators: Implements Memento pattern for SimulationSnapshot records; consumed by ReplayView.
  • OOP Concepts: Memento Pattern, Generics (History<T>), Encapsulation.
  • Why separate: Separates state storage and retrieval from active simulation execution.

9. MissionRepository & Reporter (com.orbitalix.report)

  • Purpose: Generates multi-format mission dossiers, audit logs, and telemetry exports.
  • Responsibilities: Implements the Visitor pattern. Traverses mission telemetry to render responsive HTML5 dashboards, flat CSV spreadsheets, and ANSI terminal text.
  • Collaborators: ReportVisitor interface, HtmlReportVisitor, CsvVisitor, MissionReport.
  • OOP Concepts: Visitor Pattern, Open/Closed Principle.
  • Why separate: Allows adding new export formats (e.g., JSON or XML) without modifying domain models.

10. Main.java (com.orbitalix.app)

  • Purpose: Clean application bootstrap and CLI command-line entry point.
  • Responsibilities: Parses command-line arguments (--cli, --selftest, --screenshots), initializes the simulation controller, and safely launches the Swing desktop GUI on the Event Dispatch Thread (EDT).
  • Collaborators: Instantiates DefaultSimulationController and MainWindow.
  • OOP Concepts: High Cohesion, Separation of Concerns.
  • Why separate: Keeps startup parsing isolated from application logic.

Architectural Summary

By studying OrbitalX, you have seen how:

  • Classes and Objects model physical spacecraft, missions, and consumables.
  • Encapsulation prevents illegal state mutations and protects critical telemetry invariants.
  • Abstraction hides mathematical complexity behind clean, high-level interfaces.
  • Inheritance organizes hardware and crew into reusable, specialized hierarchies.
  • Polymorphism allows the simulation engine to operate uniformly across heterogeneous subsystems.
  • Layered Architecture cleanly separates presentation, business logic, and persistence.
  • SOLID Principles produce an enterprise-grade codebase that is easy to extend, test, and maintain.
